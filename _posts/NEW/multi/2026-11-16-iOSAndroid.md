# iOS와 Android에서 C++ 코드 부르는 법

---

## iOS: .mm (Objective-C++)

- `.mm` 파일에서는 Objective-C와 C++을 한 파일 안에서 섞어 쓸 수 있다.
- ObjC는 C에 문법 몇 개를 얹은 언어다. clang이 ObjC 메서드 호출을 `objc_msgSend()`라는 C 함수 호출로 바꾼다. 그래서 C++ 코드와 자연스럽게 섞인다.
- iOS는 빌드할 때 링커가 모든 코드를 실행 파일 하나로 합치면서 함수 짝을 확인한다.
- ObjC 객체가 C++ 엔진 쪽으로 넘어가면 ARC는 더 이상 그 객체를 추적할 수 없다. 그래서 사람이 `retain`/`release`로 소유권을 명시하는 편이 관리하기 쉽다.

## Android: JNI

- Android는 **JNI(Java Native Interface)**로 C++을 부른다.
  - C++ 엔진을 `.so` 라이브러리로 빌드하고, **실행 중에** 불러온다(로드 코드가 실행될 때).
  - Java 쪽에는 본문 없는 `native` 메서드만 선언하고, 실제 구현은 C++ 파일에 있다.
  - Java 컴파일러는 `native` 선언만 확인하고, C++ 컴파일러는 Java를 모른다. C++ 쪽은 그냥 평범한 함수 이름이다.
- Java의 `int`는 C++에서 `jint`로 받는다. 이렇게 두 세계의 타입을 맞춰 바꾸는 것을 **마샬링**이라고 한다. C++ 함수는 항상 `JNIEnv*`와 `jobject`를 추가로 받는다.
- 흐름: 버튼을 누름 → `native` 메서드 호출 → JNI가 `.so`에서 이름으로 찾음 → C++ 함수 실행

## JVM과 ART

- **JVM**: Java 소스를 빌드하면 `.class`(바이트코드)가 나온다. CPU는 이걸 직접 못 읽고, JVM이 읽어서 실행한다.
- **ART(Android Runtime)**: Android 기기에는 JVM이 없다. `.class` → `.dex`로 바꾸고 ART가 실행한다.
  - `Java 소스 → (javac) → .class → (D8) → .dex → ART → CPU`
  - ART는 객체를 만들고 GC로 지우고, 스레드를 관리하고, JNI를 연결해 준다.
- Android 빌드는 Java(dex)와 C++(so)를 따로 빌드해 APK에 담고, ART가 실행 중에 이어 준다.

## 두 세계의 메모리

- ART의 GC는 **Java 객체가 사는 영역만** 본다. C++가 `new`로 만든 객체는 GC 눈에 안 보인다.
  - 그래서 C++ 객체는 GC가 지워 주지 않는다. 직접 `delete`해야 한다.
  - C++가 Java 객체를 들고 있어도 GC는 모른다. 그래서 `NewGlobalRef`로 "내가 쓰고 있다"고 알려야 한다(iOS의 `retain`과 같은 역할).
- 정리할 때는 C++ 소멸자에서 하위 C++ 객체를 `delete`하고 `DeleteGlobalRef()`로 Java 객체를 놓아 준다.
- Java 객체 쪽에서 C++ 객체를 찾을 때는, C++ 객체의 주소를 Java 객체 안에 `long`으로 저장해 두고 `native` 메서드가 불릴 때 그 값으로 인스턴스를 꺼낸다.

# C++ · ObjC · Java 사이의 소유권

---

| 상황 | iOS | Android |
|---|---|---|
| C++가 UI 객체를 **소유** | ObjC 쪽에서 `retain` | C++에서 `NewGlobalRef` |
| C++가 UI 객체를 **가리키기만** | `void *`로 보관 | `NewWeakGlobalRef` |
| UI가 C++ 객체를 **소유** | C++ 객체를 들고 직접 해제 | Java 객체가 C++ 주소(`long`)를 들고 있음 |

# 멀티플랫폼에서 MRC가 유리한 이유

---

- C++ 공통 엔진 위에 iOS는 `.mm`, Android는 JNI로 플랫폼 층을 얹은 구조다.
- 엔진은 플랫폼을 모르고 C++ 인터페이스만 정의한다. iOS는 그 인터페이스를 구현해 ObjC 세계로 넘긴다.
- iOS 코드는 ARC 이전부터 만들어져 왔고, C++ 엔진으로 넘어간 ObjC 객체는 ARC가 추적하기 어렵다. 그래서 명시적으로 소유권을 갖도록 MRC를 쓴다.
- Android는 같은 엔진을 JNI로 연결하는데, GC가 네이티브 메모리를 못 보기 때문에 GlobalRef 같은 것으로 소유권 문제를 푼다.

# GC와 ARC

---

- **ARC**: 붙잡은 수를 +1/−1 하다가 0이 되는 순간 바로 해제한다. 시점이 예측 가능하다. 서로 붙잡는 순환 참조는 못 풀어서 `weak`가 필요하다. C++의 `shared_ptr`와 비슷한 구조다.
- **GC**: **루트**(실행 중인 함수의 지역 변수, static 변수, 살아 있는 스레드)에서 참조를 따라가 닿는 객체에 표시하고, 표시 안 된 것을 치운다(Mark & Sweep).
  - "서로 잡고 있나"가 아니라 "루트에서 닿나"를 보므로 순환 참조도 치운다.
  - 대신 정리 시점이 GC가 돌 때라 불확실하고, 도는 동안 잠깐 멈출 수 있다.
  - 대부분의 객체는 금방 버려지므로 새 객체 영역(Young)은 자주, 오래 산 객체 영역(Old)은 가끔 청소한다(세대별 수집).
- GC가 있어도 static 변수처럼 오래 사는 루트가 계속 붙잡고 있으면 안 치워진다. 이건 GC 언어에서도 누수다.

# 메모리 누수 수정

---

- 고객사에서 뷰어를 닫아도 메모리가 해제되지 않는다는 제보를 받았다. Instruments와 Xcode 메모리 그래프로 보니 실제로 객체가 수천 개씩 쌓이고 있었다.
- 뷰어는 JS 엔진을 내장하고 있어서, 보고서에서 JS 명령이 오면 실행한다. C++ 객체를 JS에 넘기려면 래퍼가 필요한데, 래퍼를 꺼낼 때 `retain`을 하면서 **재사용할 때도 매번** `retain`하고 있었다. 재사용일 때는 하지 않도록 고쳤다.
- Instruments는 시간 흐름에 따른 할당 기록이고, 메모리 그래프(memgraph)는 한순간의 객체 그래프 스냅샷이다.

# 성능 개선: 서명 컴포넌트 4초 멈춤

---

- 외장 인감 스캐너를 연동하던 중, 서명 컴포넌트를 처음 누르면 화면이 4초간 멈추는 문제가 있었다. 메인 스레드가 막히는 전형적인 Hang이었다.
- 벤더 SDK 초기화 함수가 4초를 잡아먹고 있었다. 소스가 없는 라이브러리라 안을 고칠 수 없었다.
- 콘솔 경고로 그 4초 동안 **오디오 준비**가 일어나고 있다는 걸 찾았다. iOS의 `prepareToPlay`는 오디오 엔진, 오디오 서버 통신, 디코더 하드웨어를 한 번에 올린다.
- 앱 프로세스당 한 번만 드는 비용이라, 앱 시작 시점에 백그라운드에서 미리 준비만 시켜 두었다. 실사용에서 4초 → 약 0.1초 수준이 됐다.
- 벤더 SDK 초기화 자체를 백그라운드로 옮기지는 않았다. 스레드 안전이 보장되지 않고 콜백이 메인 스레드 기준이었기 때문이다.

# 모든 것이 메인 스레드 기준인 이유

---

- 엔진은 MFC 기반으로 태어났다. Windows UI는 UI 스레드 하나 + 메시지 루프로 처리되고, 창은 만든 스레드에서만 건드린다.
- 다른 스레드가 UI에 일을 시키려면 `SendMessage`(끝날 때까지 기다림) 또는 `PostMessage`(안 기다림)로 부탁해야 한다.
- 그래서 엔진 코드는 "한 스레드가 메시지를 순서대로 처리한다"는 가정 위에 짜여 있다. iOS·Android 지원은 그 뒤에 생겼고, 플랫폼 층도 이 구조를 따른다.

| 개념 | iOS | Android |
|---|---|---|
| 스레드 하나에서 도는 메시지 루프 | RunLoop | Looper |
| 루프가 꺼내 처리하는 큐 | main queue | MessageQueue |
| 특정 루프의 큐에 일을 넣는 도구 | `DispatchQueue.main` | `Handler` |
| 큐에 넣고 바로 돌아오기 | `main.async` | `handler.post` |

# 고객 환경에서만 나는 문제 해결

---

- 보험사 모바일 상담 앱에서, 특정 스크롤 위치에서 서명을 누르면 서명창이 바로 닫히는 문제가 있었다. 사내에서는 재현되지 않았다.
- 고객사가 자료 반출을 꺼려서, 호출 경로를 로그로 남기는 디버깅용 빌드를 만들어 보냈지만 원인을 특정하지 못했다.
- 고객사는 임시 우회 기능을 요구했고, 원인을 아무도 모르니 요구대로 해 주자는 방향이었다. 나는 우리 쪽 문제가 아닐 거라고 보고, 직접 가서 고객 코드를 보고 오겠다고 했다. 다녀와서도 모르면 반영하자고 했다.
- 가 보니 앱이 오토레이아웃 제약을 뷰어 내부에 걸어 두어, 서명창 때문에 줄어든 뷰가 원래 크기로 되돌아가면서 서명창이 닫히는 문제였다. 올바른 SDK 사용법과 잠재 위험을 안내하고 왔다.

# Toto: 웹 ↔ 네이티브 브리지 SDK

---

## 무엇인가

- 웹 페이지에서 OZ 뷰어, 카메라 같은 네이티브 기능을 쓸 수 있게 해 주는 SDK다.
- 웹뷰를 만들 때 브리지 JS를 문서 시작 시점에 주입하고, 메시지 핸들러를 하나 등록한다.
- 웹에서 네이티브를 부르면 JS가 `postMessage`로 런타임 ID, 명령, 인자를 보내고, 네이티브가 메서드를 실행해 결과를 보관한다.
- 네이티브에서 웹으로는 이벤트를 보낸다.
- 외부에 공개되는 `OZTotoWebView`(UIView)가 내부에 `WKWebView`를 소유하는 구조다.

## 동기 반환을 만드는 방법: prompt

- `postMessage`는 웹 표준이 아니라 **WebKit이 넣어 주는 객체**다. 보내기만 하고 반환값이 없다.
- WKWebView는 JS를 앱과 **다른 프로세스**에서 실행한다(웹 페이지 때문에 앱이 멈추지 않게). 그래서 JS가 네이티브를 멈춰 기다리는 정식 API가 없다.
- 하지만 `prompt()`는 웹 표준이 "끝날 때까지 JS를 멈춘다"고 정해 둔 함수다. 이 통로를 이용해, 네이티브의 prompt 대리자가 대화창 대신 **실행 결과 문자열을 반환**하게 했다.
- 호출 흐름: JS 호출 → 브리지 JS → 네이티브 메시지 수신 → 명령 형식 검사 → 대상 객체 찾기 → 이름으로 메서드 찾기 → 실행 → prompt로 결과 반환

## 이름으로 메서드 부르기: ObjC → Swift

- ObjC는 클래스마다 **이름 → 함수 주소** 표를 실행 중에도 들고 다닌다. 그래서 `objc_msgSend`로 문자열 이름만으로 메서드를 찾아 부를 수 있었다.
- Swift는 컴파일할 때 "여기서는 이 주소로 가라"를 미리 넣는다. 이름으로 찾는 표를 만들지 않는다(`@objc`를 붙인 것만 ObjC 표에 올라간다).
- `@objc`로 ObjC 런타임에 계속 기대면 생기는 문제:
  - ObjC로 표현 못 하는 Swift 타입(struct, 연관값 enum, 제네릭, `Int?` 등)을 그 메서드의 인자·반환에 못 쓴다.
  - 이름으로 부르면 컴파일러 검사를 건너뛰어서, 틀린 호출은 실행해 봐야 안다.
  - 목록에 오른 메서드는 `dealloc` 같은 위험한 것까지 웹에서 부를 수 있다.
  - ObjC 메타데이터 때문에 앱 크기가 커진다.
  - `@objc`는 ObjC 쪽에서 Swift 함수를 반드시 불러야 할 때 쓰는 것이다.
- 그래서 **클래스마다 "JS 이름 → 메서드" 람다를 해시맵에 등록**하는 구조로 바꿨다. 등록할 때 제네릭으로 인자 개수·타입 검사 코드가 자동으로 붙고, 틀린 호출은 실행하지 않고 null을 돌려줘 앱이 죽지 않는다. 웹에서는 등록한 메서드만 부를 수 있다.
- 첫 Swift 버전은 함수 주소(IMP)를 꺼내 `unsafeBitCast`로 형변환해 불렀는데, 모든 메서드를 같은 모양으로 불러야 해서 Bool 반환 등에서 위험했고, 인자 수만큼 콜론이 붙는 셀렉터 이름이 JS 이름과 맞지 않았다. 그래서 등록 테이블로 바꿨다.

## VTable이라는 이름

- C++ vtable은 상속한 클래스가 메서드를 오버라이드했을 때, **실행 중에** 어느 쪽을 부를지 고르는 장치다.
  - 클래스마다 함수 배열을 만들고, 객체 맨 앞에는 자기 클래스의 배열을 가리키는 포인터(vptr)가 있다.
  - 컴파일러는 "이 메서드는 몇 번 칸"까지만 알고, 실행 중에 vptr → 배열 → 그 칸을 따라가 실제 함수를 얻는다.
- Toto의 VTable은 칸 번호가 아니라 **이름으로 찾는 디스패치 테이블**이다(딕셔너리에 클로저를 넣은 것). "표를 보고 실행 중에 함수를 고른다"는 점에서 이름을 빌렸다.

## 두 언어를 한 빌드에 두고 옮기기

- ObjC와 Swift를 한 프로젝트에 같이 두고, 다른 클래스에 덜 의존하는 클래스부터 핵심(웹뷰·런타임) 쪽으로 한 칸씩 옮겼다. 매 단계 빌드되고 동작하는 상태를 유지했다.
- 처음에 동료는 일정과 영향 때문에 최소 수정을 원했다. 한 번에 바꾸는 위험이 걱정이라는 걸 알고 작은 범위부터 단계적으로 하자고 제안했고, 관리자 승인을 받아 진행했다.
- 두 언어를 잇는 통역 파일:
  - Swift → ObjC: ObjC 헤더를 Swift에 보여 준다. 앱은 **브리징 헤더**, 프레임워크는 **엄브렐러 헤더**(모듈맵의 입구).
  - ObjC → Swift: 컴파일러가 `모듈이름-Swift.h`를 자동으로 만든다. `@objc`로 노출한 것만 실린다.
- 비유: C++ 프로젝트에 C 코드를 섞을 때 `extern "C"` 헤더를 쓰는 것과 비슷하다.
  - C++ 컴파일러는 오버로드·네임스페이스 때문에 함수 이름을 맹글링한다.
  - `extern "C"`는 맹글링을 끄고 C 이름 그대로 내보낸다. C++로 만든 함수를 C++ 밖에서 부를 때, C++이 C 함수를 부를 때 경계 헤더에 쓴다.
  - Swift에서 그 역할을 하는 게 `@objc`다.

# eformsign 앱 전환

---

- 메인 화면 클래스 하나에 웹 이벤트 처리와 오프라인 기능이 다 몰려 있던 앱을, **Clean Architecture의 층 구조를 따른 MVVM**으로 새로 썼다.
  - Presentation: View와 ViewModel (UI)
  - Domain: UseCase(동작), Entity(업무 데이터), Repository **프로토콜**(데이터 요청 약속)
  - Data: Repository **구현**, DataSource, 서버·푸시 원본 모양(DTO, 이 앱에선 Model)
  - 의존 방향: `Presentation → Domain ← Data`
- 정석은 "경계를 넘는 건 Entity뿐"이지만, 이 앱은 일부 기능에서 Data의 모델이나 웹뷰 SDK 타입이 Domain까지 들어와 있어 의존 규칙을 엄격히 지키지는 못했다. 층을 별도 모듈로 나누면 컴파일러가 이걸 막아 준다.
- 주소 검색 예시:
  - View: 검색 버튼에 ViewModel 함수를 연결
  - ViewModel: UseCase에 검색어를 넘기고, 결과를 `@Published`로 받아 화면을 갱신
  - UseCase: Repository 프로토콜에 요청하고 결과를 업무용 Entity로 돌려줌
  - Repository 구현: 실제 서버에 요청
  - Service: 네트워크 통신(URLSession)
- **Swift 6 언어 모드**로 처음부터 작성했다. 데이터 경합을 컴파일 에러로 막는다.
  - 다른 스레드로 넘기는 값은 `Sendable`이어야 한다.
  - 메인 스레드에서만 읽어야 하는 값을 아무 데서나 바로 읽을 수 없고, 메인으로 넘겨서 읽어야 한다.

# OZSync: 실시간 동기화 SDK

---

- 여러 기기가 같은 전자문서를 실시간으로 함께 보고 입력하는 SDK다. 상담원 PC와 고객 모바일처럼 서로 다른 플랫폼에 띄운 같은 서식의 입력과 페이지 이동을 서버를 거쳐 맞춘다.
- 2018년에 만든 ObjC 샘플 앱이 있었지만, 그걸 옮긴 게 아니라 Android·웹 SDK를 기준 스펙으로 삼아 Swift SDK로 새로 만들었다.
- 통신: 인증과 방 입장은 HTTP POST, 이후 실시간 송수신은 설정에 따라 **HTTP 롱폴링(기본)** 또는 **WebSocket**.
- 연결 상태 8개 상태 머신(대기, 인증 대기, 방 입장 대기, HTTP 준비 2단계, HTTP 수신, WebSocket 수신, 복구 포기).
- 재연결: 1초 → 2초 간격으로 다시 시도하고 세 번째 끊김에 포기. 10초 이상 버틴 연결만 성공으로 쳐서 재시도 횟수를 초기화한다.
- 송신: 입력을 바로 보내지 않고 0.2초 모아 한 번에 보낸다. WebSocket은 throttle, HTTP는 debounce. 수신은 뷰어가 그리는 동안 온 명령을 큐에 쌓았다가 순서대로 실행한다.
- 연결 상태, WebSocket, 송신 큐, 상대 기기 점검을 각각 actor가 소유한다. 다만 actor는 await 사이 재진입은 못 막는다.

## HTTP 기본

- 메서드: GET 가져오기, POST 새로 만들기·처리 요청, PUT 통째로 바꾸기, PATCH 일부만 바꾸기, DELETE 지우기
- 상태 코드: 2xx 성공(200 OK, 201 만들어짐), **3xx 이동**(301 영구, 302 임시, 304 바뀐 것 없음), 4xx 요청 쪽 잘못(400 형식 틀림, 401 로그인 필요, 403 권한 없음, 404 없음, 429 요청이 너무 많음), 5xx 서버 쪽 잘못(500, 502, 503)

# AI가 만든 코드를 어떻게 믿었나

---

- AI를 믿는 게 아니라 검사를 믿는다.
- 반영 전에 빌드, 실서버·실기기 확인, 기존 구현과의 대조, 백지 상태 세션의 교차 검증을 거치게 해서 실수가 걸러지게 했다.
- 많은 코드를 모두 같은 깊이로 보지 않는다. 전체 흐름과 경계는 이해하고, **되돌리기 어려운 곳**(메모리, 좌표 계산)과 **고객에게 바로 나가는 곳**(공개 API) 위주로 본다.
- 전부를 똑같이 의심하는 것보다, 어디를 사람이 봐야 하는지 아는 게 실력이라고 생각한다.

# AI가 틀린 적은

---

- 보안 조치를 조사하던 중, AI 에이전트가 코드를 검색해서 "그 함수는 없다"고 보고한 적이 있다.
- 확인해 보니 오래된 C++ 소스 일부가 한글 주석 때문에 **CP949**로 저장돼 있었다. 에이전트 셸의 grep은 내장 검색기를 "UTF-8 고정 + 바이너리 파일 건너뛰기" 옵션으로 실행하고 있었는데, UTF-8 기준으로는 CP949 한글이 깨진 바이트라 그 파일을 바이너리로 보고 통째로 건너뛰었다.
- 그대로 믿었으면 핵심 함수를 놓칠 뻔했다.
- 그 뒤로 그 저장소에서는 **훅**으로 막았다. Bash 명령이 실행되기 직전에 명령 문자열을 받아서, UTF-8이 아닌 파일을 grep으로 검색하려 하면 거부하고 이유를 붙인다. 그러면 Claude가 그 이유를 읽고 rg로 다시 검색한다.
- grep을 rg로 글자만 바꿔 실행하지 않은 이유: 두 도구는 같은 옵션 글자의 뜻이 다르다(grep `-r` = 재귀, rg `-r` = 치환). 글자만 바꾸면 에러 없이 틀린 결과가 나온다.

# Swift ↔ ObjC 경계에서 주의할 점

---

- **Swift에서 ObjC를 쓸 때**
  - ObjC 헤더에 `nullable`/`nonnull` 표시가 없으면 Swift에서 암시적 언래핑(`!`) 타입으로 들어와, nil이면 바로 크래시가 난다. 헤더에 표시를 붙인다.
  - ObjC 예외(`NSException`)는 Swift의 `do-catch`로 잡을 수 없다. ObjC 쪽에서 잡아 `NSError`로 바꿔 넘긴다.
- **ObjC에서 Swift를 쓸 때**
  - ObjC가 표현할 수 있는 타입만 넘어간다. Swift 구조체, 연관값 enum, 제네릭, 옵셔널 Int 같은 건 노출이 안 된다. 경계에 놓이는 API는 클래스나 기본 타입으로 맞춘다.
